# 问题、处理过程与验证结果

现场记录中的节点名称已统一用角色表示。文档和数据文件中的 `primary` 为主节点，`backup-1` 至 `backup-3` 为按优先级排列的备用节点。时间、响应码和切换结果均取自同一次现场测试。

| 现场现象 | 定位与处理 | 验证证据 |
| --- | --- | --- |
| 手机连上热点后提示无网络，百度偶尔打不开 | 手机端复现 DNS 约 0.26 秒完成，TCP 在 7 秒内未建立。前台加载期间最多有 35 条已发出数据的连接排队。启用预留 zram，将有效 TCP 转发并发提升至 16，保留 DNS 和检查容量，并调整空闲连接回收 | [初始请求](../evidence/phone-initial.json)、[队列采样](../evidence/queue.json) |
| 页面并发访问期间偶发误判掉线 | 新节点先完成 HTTPS 证书和返回码检查。已在线时，如果两个探测站均失败，继续检查本轮是否有最近 12 秒内经加密链路真正交付给手机的新数据。首轮失败保留已有会话，连续两轮失败切换 | [管理程序](../device/manager.sh)、[故障演练](../evidence/failover.json) |
| 浏览器尝试 UDP 443 后等待 | 热点仅转发 TCP，设备向 QUIC 请求返回端口不可达。DNS 复用一条经过当前节点的 TCP 连接，并支持 UDP 截断和 TCP 补查 | [防火墙](../device/firewall.v4)、[DNS 与 HTTPS 转发验证](../evidence/forwarding.json) |
| 设备重启后偶发缺失上游路由或时间失准 | DHCP 租约记录 USB 网关，启动时补回默认路由；Windows 检测到设备后校时并重新装入 RAM 核心 | [重启记录](../evidence/reboot.json) |
| 旧核心未能完成现用 REALITY 握手 | 在 ARM 设备运行 v2.0.0，使用精简线程配置。新增核心约 2.98 MB，从 Windows 装入 RAM，可写分区保留四条配置和控制程序 | [构建说明](build.md)、[设备安装核验](../evidence/installation.json) |
| 第三个备用节点未能接替转发 | 本次测试中，主节点和前两个备用节点均获得过有效的 HTTP 204 和 200。第三个备用节点的两项 HTTPS 探测均超时 | [逐节点检测](../evidence/nodes.txt)、[实际切换顺序](../evidence/failover.json) |

## 手机和网络

测试时关闭移动数据，手机只连接纽曼热点。Wi-Fi 网关是 `192.168.0.1`，手机网络请求绑定 `wlan0`。四轮访问三个网站和三个联网检测地址共 24 次，24 次均成功。Android 四轮均把热点标记为已验证，设备使用主节点转发。[手机请求明细](../evidence/phone-network.json)

Chrome 使用新建测试标签页并关闭页面缓存。切换前 6 次页面访问全部获得 HTTPS 200 并读取到正文或搜索控件。其中百度两次分别在 4.88、9.75 秒达到 DOM 就绪，35 秒观察窗口结束时仍在加载。Google 两次分别在 3.74、4.02 秒触发整页加载完成事件。[切换前 6 次访问](../evidence/chrome-six-visits.json)

解除故障限制并自动恢复主节点后，手机再次访问三个站点，三个页面均完整加载，两处搜索页均检出搜索框。

| 站点 | 首次绘制内容 | 整页加载完成 |
| --- | ---: | ---: |
| 百度 | 8.23 秒 | 48.67 秒 |
| Google | 4.41 秒 | 9.89 秒 |
| example.com | 12.37 秒 | 12.56 秒 |

此次样本覆盖一台设备、一个 Windows 上游和一部 Android 手机。峰值排队解释了并发场景中的一部分延迟，外部节点和站点耗时也随时间变化。长时间稳定性仍待验证。[恢复后浏览器逐项数据](../evidence/chrome-after-recovery.json)
